# Neon London deployment contract — preparation only

**Staging NO-GO; production NO-GO. No Neon project, database or role was contacted or changed.**

The selected provider is Neon on AWS London (`aws-eu-west-2`), with `https://staging.vetthevat.com` and `https://app.vetthevat.com`. The application and worker target is Ubuntu 24.04 AMD64, Node **22.23.4 Linux x64**, recorded in `runtime.json`. This patch was checked against the [official Node archive](https://nodejs.org/en/download/archive/v22.23.4); successful validation on this patch remains a Linux CI gate. The Windows verification runtime is older and is not a releasable Linux build.

## Separate environments

Use two independently administered Neon projects in London, one per environment, with separate primary branches, databases (`vtv_saas_staging`, `vtv_saas_production`), credentials, installation UUIDs, restore histories and backup destinations. This provides the requested separation of databases, credentials and backups. Do not create staging by branching customer production data. A Neon branch is not an independent offsite backup. Project IDs, exact direct endpoint DNS names, PostgreSQL major version and selected recovery/availability plan remain private configuration inputs; none are inferred or provisioned by this package.

Use PostgreSQL 17 for compatibility review. Initial compute budgets are **2 CU for staging (approximately 8 GiB RAM) and 2 CU for production**, with 20/50 GiB initial storage budgets respectively; validate CU mapping and quotas in the purchased plan before approval. Keep fixed compute and suspend disabled for the initial latency/recovery acceptance. Enable autoscaling or scale-to-zero only after measuring cold starts, connection budgets and lease recovery. The app's short connection deadlines deliberately fail unavailable instead of assuming a sleeping database is healthy. These allocations are starting reservations, not measured capacity or purchased service guarantees. See [Neon compute sizing](https://neon.com/docs/manage/computes).

## Connection and TLS rules

Set `VTV_DATABASE_PROVIDER=neon` in every managed web/worker environment. The parser accepts London `ep-…[.c-N].eu-west-2.aws.neon.tech` direct endpoints on 5432 and rejects `-pooler` endpoints and other regions. Exact endpoint and database must also match their independent approved values. Do not use the Console's default pooled connection string. The [Neon connection reference](https://api-docs.neon.tech/reference/getconnectionuri) identifies pooled URIs by the `-pooler` suffix.

The connection URL contains only the exact role, percent-encoded password, approved direct hostname, port and database. Omit query parameters entirely. `pg` receives explicit CA, TLS >=1.2 and certificate verification options; [node-postgres warns that URL SSL parameters can replace those options](https://node-postgres.com/features/ssl). Copy a reviewed Ubuntu CA bundle to `/etc/vetthevat/<environment>/postgres-ca.pem` with root ownership and mode 0644, recording its digest and trust-store version. Verify actual Neon certificate chain/hostname privately; do not download and trust the leaf certificate as a CA or disable verification. Review trust-store updates and CA expiry as part of rotation.

Every managed checked-out connection now requires an actual authorized Node `TLSSocket`, TLS 1.2/1.3 and a peer certificate matching the approved hostname. SQL role/installation checks execute on that same pinned connection. `pg_stat_ssl` remains diagnostic: it describes the PostgreSQL backend hop and cannot prove the client's TLS session through a hosted proxy. This is an inference from the [Neon proxy/security architecture](https://neon.com/docs/security/security-overview) and the [PostgreSQL view definition](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-PG-STAT-SSL-VIEW); the exact Neon endpoint must still undergo positive and negative certificate tests. No claim is made about an internal provider hop from this client-side check. The adapter depends on the installed `pg` 8.16.3 transport structure and fails closed if that structure changes.

## Role provisioning and fresh schema approval

**Never install a Neon Console/API/CLI-created administrator role in application environment files.** Neon grants `neon_superuser` membership to roles created through those interfaces; restricted roles must be created using SQL. See [Neon's role documentation](https://neon.com/docs/manage/roles) and [database access documentation](https://neon.com/docs/manage/database-access). The runtime rejects role memberships, administrative attributes, owner privileges and unwanted CREATE/TEMP authority. Ordinary read/write group-role examples in provider docs do not satisfy this application's stricter no-membership contract.

The existing `postgres/roles.sql.template` is design material only. The Neon administrator may provision exact restricted SQL roles and owner roles **only through new, exact reviewed bootstrap files after checksum approval**. Passwords must be independently generated, meet Neon entropy requirements and be injected privately; no password literals belong in review SQL. Auth, business, document and provider role names remain fixed because existing security functions inspect session identity. `vtv_migrator` is a separate SQL-created login with only explicitly approved owner membership, never `neon_superuser`; the administrator owns initial role/database provisioning. No migrator credential belongs on web or worker hosts.

Fresh bootstrap must preserve the approved logical schema and corrected functions through 021, FORCE RLS, fixed definer search paths, revoked PUBLIC grants and precise function allowlists. Existing local migration files and runner remain unchanged. They include local cluster/operator guards and cannot be run on Neon. Do not replace those guards or point `local:launch` at Neon.

Before rendering executable migration candidates, record exact project/branch IDs, direct endpoint, fresh database names, PostgreSQL version, intended schema owner authority, existing database contents, backup/restore plan and installation UUIDs. Each resulting file needs its own filename, SHA-256, target and separate user approval. No executable migration is ready for approval in this package; selecting a provider does not approve SQL execution.

## Backup, RLS and acceptance

Record the actual purchased Neon restore window, suspend behaviour, connection limit and regional recovery options. Proposed 7/30-day recovery windows and RPO/RTO are requirements to validate, not promises that the selected Neon plan supplies them. Independent encrypted logical backups and R2 originals recovery remain mandatory. A full dump of FORCE RLS tables needs separately approved administrative backup authority; do not give runtime roles BYPASSRLS or silently accept filtered archives. Never put Neon management API keys on web or worker services.

Before any GO decision, use deliberately synthetic data in the new staging project: verify every service's current/session role and installation binding, forbidden owner/membership privileges, two-company/foreign-session denial, concurrent final quotas, actual TLS socket proof and invalid-CA/hostname rejection. Run independent workers against durable jobs, kill after claim and during uncertain acknowledgement, wait for lease expiry and verify one financial effect. Restore an independently downloaded/decrypted backup into an explicitly approved new recovery project/database and verify financial totals, RLS, role grants and original bytes. Nothing in this document or a configured boolean passes those gates.
