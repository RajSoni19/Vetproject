# Milestone 3C.1 — static migration security review

Reviewed the current `database/drafts/001_vat_core.review.sql` and
`002_read_isolation.review.sql`; neither was executed or modified. Findings below
are verified from source, not evidence of deployed tables or privileges. The owner
reports successful 17.11 dev/test runtime logins, but no query output was received
or independently reproduced. No password reset is needed or authorized.

## Findings and required disposition

| Priority / reference | Verified source finding | Required before later implementation/cutover |
| --- | --- | --- |
| Critical — `002`, `member_read`, `own_membership_read` | RLS trusts mutable `app.user_id` and `app.company_id` session settings. An active-member join is useful but is not authenticated identity. A holder of runtime credentials could supply another user's context. This milestone does not assign or spoof context. | Keep credentials exclusively server-side; verify Firebase identity, active membership and capability on every operation; parameterized DAL SQL; transaction-local context set only after authorization. Decide whether direct-runtime compromise requires a stronger database trust boundary. Real two-user/two-company and pooled-context tests are required later. |
| High — `002`, `member_read` loop | Any active member with table grants can read every row in its selected company on all listed tables, including audit, original metadata, idempotency responses and legacy mappings. There are no role/capability checks. Company archive state is not checked. | Approve a capability matrix and minimize table/column grants and returned DTOs. Document download, exports, audit and sensitive admin data require separate checks. Archived-company read policy is an explicit decision. Do not grant blanket SELECT merely because RLS exists. |
| High — `002`, `own_membership_read` and `own_user_read` | Membership's self-read policy does not itself check app_users.status; a disabled user can still satisfy its membership policy if context and SELECT are supplied. The generic policies join app_users and therefore require an active user. | Align membership visibility/disabled-user policy. An empty or absent context fails closed; malformed UUID context errors rather than granting access. Test all cases later. |
| High — `001`, `CREATE SCHEMA vat`; both files' transaction boundaries | No owner is specified. Objects belong to the effective creating role, not automatically to the database owner. The files commit separately, leaving a possible window between table creation and RLS. | Before future DDL, explicitly verify intended effective owner. Migrator must be permitted to assume its NOLOGIN owner but runtime must not. Review one atomic schema+RLS deployment or prove no runtime/public exposure between commits. No role assumption was executed here. |
| High — `001` schema revocation; `002` no grants | Revoking PUBLIC schema access is useful but does not establish database CONNECT/TEMP, per-role schema grants, function EXECUTE defaults or the actual creator's default ACLs. Existing global default grants can affect new objects. | Review C06/C07/C12/C13 results in EACH database, under both owner and migrator creator identities. Default ACLs follow the effective creator, not inherited-role defaults; schema-local ACL additions do not remove global defaults. Public function EXECUTE is a specific future risk. |
| High — `002`, identities/web_sessions policies | Both tables have forced RLS and no runtime policy. This is deny-by-default, but the proposed identity/membership bootstrap is not operational. No write policy exists anywhere in `002`. | Design a narrow, separately reviewed bootstrap path. Do not solve it with a superuser pool, owner credentials in the app, unrestricted SECURITY DEFINER functions, or disabling RLS. Future writes require action policies/commands, audit and tests. |
| High — `002`, RLS scope / existing privilege paths | RLS does not govern TRUNCATE or REFERENCES. No write policy is not proof that every data-changing path is blocked if existing/default grants allow TRUNCATE, sequence advancement or callable privileged routines. The draft does not create such routines, but actual cluster paths remain unknown. | Review effective relation/sequence/routine privileges, views, indirect roles and defaults before any grants. Require explicit denial of unapproved TRUNCATE and privileged routine execution; do not rely on RLS alone. Constraint failures can reveal existence across tenant boundaries, so redact database details at the API and avoid attacker-chosen global keys. |
| High — `001`, invoices/lines/VAT groups | Header net+VAT=gross is checked only for status Reviewed. No cross-row header/line/VAT-group sum enforcement, required line count, line arithmetic/rate calculation, or verified-state consistency exists. Processing Confirmed can coexist with incomplete financial data. | Reuse the existing approved rounding policy in an atomic save/verify service; reject mismatches and invalid status transitions. Decide deferred DB constraints/triggers versus exclusive reviewed command access. Drafts must retain optional fields; do not invent missing amounts. |
| High — `001`, invoice_lines / invoice_vat_groups / source amounts | NUMERIC avoids binary floating-point but rounds excess scale on storage. Quantity, prices, discounts and line/group amounts lack finite/sign/business bounds. PostgreSQL NUMERIC NaN can satisfy NaN equality, so net+VAT=gross alone does not reject it. Header range checks help header values only. | Validate canonical decimal strings, finite values, allowed scale/ranges and existing sign policy before storage; add approved DB checks as defense in depth. Review raw/source preservation for rejected imports. No financial policy change is approved by this review. |
| High — `001`, bank_allocations | No aggregate ceiling prevents concurrent allocations exceeding transaction or invoice balances. No active transaction+invoice uniqueness, currency/direction checks, invoice eligibility rules or immutable bank-account currency exists. | Lock transaction and invoice rows in a deterministic order; check all active allocations and exact minor-unit balances atomically. Add version/idempotency guards and two-connection race tests. Choose an active-pair uniqueness policy; preserve valid partial/split payments. Reversal must retain immutable history, author and reason. |
| High — `001`, audit_events / invoice_revisions | Append-only and immutable history are comments, not enforcement. Current absence of write policies/grants blocks ordinary writes, but future blanket DML would undermine the intended boundary. Revision snapshots and legacy audit payloads have no structural/provenance validator. | Grant only reviewed commands; prevent ordinary UPDATE/DELETE/TRUNCATE and owner impersonation. Ensure trusted actor, revision and audit event are atomic with each change. Imported history must be marked as legacy evidence. Owners/superusers remain trusted administrators even with FORCE RLS. |
| Medium — `001`, invoice_duplicate_lookup / idempotency_keys | Duplicate lookup is nonunique, normalised number is optional and no reservation/advisory locking exists. Idempotency primary key/digest is promising, but no command compares digests, reserves work or atomically stores a result. | Define company+canonical supplier+normalised number identity for verification, including missing identity and legacy exceptions. Race-test concurrent confirmation and same-key/different-payload rejection. Do not deduplicate genuine identical lines. |
| Medium — `001`, company-qualified FKs | Company/supplier/document/invoice and banking FKs generally block cross-company links. Bank transaction's composite import FK also enforces account consistency. However invoice supplier can differ from its document's supplier within the same company; document association and reviewer actor semantics are not fully constrained. | Validate supplier/document association and membership at operation time. Do not require a historical actor to remain a current member solely to retain history. Confirm intended multi-invoice PDF policy before the unique document-owner index is adopted. |
| Medium — `001`, bank_transactions/imports | Source-row uniqueness per import is absent; fingerprint/occurrence uniqueness alone does not prove a genuine bank duplicate. File checksum may be NULL. | Require validated original manifest when available and stable import/row identity, with explicit missing-original states. Preserve identical genuine bank rows. Test repeated upload, retries and partially failed imports. |
| Medium — `001`, documents | Available requires key/size/hash, but permits empty keys, zero bytes, unbounded files and no MIME signature proof. DB checks do not prove object existence, access privacy, version integrity or malware handling. | Authorize upload/download; validate actual bytes/size/checksum/type and storage state transitions. Use immutable private object versions and audited reattachment; ambiguous supplier matches stay Needs Review. No permanent bearer URL or blob URL is a durable key. |
| Medium — `001`, dates/legacy_mappings | DATE validates normal calendar input but PostgreSQL special infinite dates are not excluded. Legacy mappings lack typed target FKs/import-batch provenance and raw source retention. Other company settings/support/notifications/invitation journeys are not covered by this core draft. | Validate finite, supported dates without silently substituting today. Preserve source IDs/raw snapshots, reviewed ownership mappings and reconciliation manifests. Add separately reviewed feature-preservation migrations before cutover. Never treat local Team roles as authenticated memberships. |
| Medium — `001`, foreign-key access paths | Missing useful leading indexes include documents(company_id,supplier_id), invoices(company_id,invoice_date/id), invoice_warnings(company_id,invoice_id), bank_allocations(company_id,transaction_id) and (company_id,invoice_id), bank_transactions(company_id,import_id,source_row), bank_imports(company_id,document_id), and company_members(user_id,company_id). | Confirm workload/query plans later; index child FKs and allocation aggregates before scale/concurrency tests. Existing company+supplier duplicate index and ordered line/group/revision keys are worth preserving. No index is created in this milestone. |

## Preserved strengths

Company-qualified foreign keys, NOLOGIN-owner architecture direction, nullable
draft identity, exact NUMERIC/BIGINT transport, explicit nullable tax metadata,
ordered non-deduplicated lines, document missing/quarantine states, revision/audit
tables and forced RLS are sound foundations. They are not a complete security or
financial enforcement implementation. No SQL in this package creates a write path.

## Before requesting synthetic migration approval

1. Owner runs the six verification entry scripts and reviews all sections. Record
   both cluster identifiers, role matrices, default ACLs and ordered HBA conclusions.
2. Resolve findings that block isolated DDL, especially creator ownership, inherited
   defaults, existing schema objects and any role/environment privilege leaks.
3. Approve exact revised SQL/checksums, execution identity and atomic execution
   approach in a separate change. Do not apply the old public-schema baseline.
4. Approve **test database only**, synthetic fixtures only, no dev/production writes,
   no resets/drops, and stop on unexpected existing objects. Review backup/restore
   and non-destructive failure handling. RLS/concurrency tests needing writes or
   transaction context changes require that explicit scope too.

This review does not request immediate execution approval: actual cluster evidence
and revised SQL are still needed before a concrete migration can be approved.
