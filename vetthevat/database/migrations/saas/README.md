## Identity and company authorization

The existing PostgreSQL identity implementation can be opted into this NEW
instance with BOTH explicit local selectors. `businessServices()` refuses mixed
authentication/business host, port, database or origin. Fresh isolated accounts
must verify their email before a live session is accepted. New accounts do not
automatically receive a company, a software administrator grant or a subscription.

Membership is the foreign-key relation `web_auth.company_memberships(user_id,
company_id)`. The user UUID comes from the server-validated opaque session, never
from a browser role, email or untrusted user ID. Company membership roles resolve
through normalized role/permission tables. Software administrator remains separate
and gives no implicit company access. Company selection is session-owned and
requires live membership.

The request wrapper validates the session, origin, CSRF and rate policy. The
transaction wrapper verifies target/database role/fingerprint, sets only a hashed
session token and company selector transaction-locally, and invokes a fixed
search-path security definer. The function checks active/verified user, live
session, active membership, company/account status and permission. Shared row
locks serialize authorization changes against the business operation. Forced RLS
repeats scope checks; client-provided company IDs never establish authority.
Commit acknowledgement is mandatory; swallowed SQL failures, parallel/pending
transaction misuse and ambiguous commit outcomes cannot publish success or retry
a callback automatically.

Financial APIs remain disabled and the new services are not mounted by a route.
Real PostgreSQL tests of function grants, locking, revocation races and RLS must
pass after migration approval before enabling any business endpoint.

## Private documents

The adapter uses an explicitly selected isolated S3-compatible endpoint and
explicit credentials. It cannot discover production AWS credentials. A private,
versioned bucket is required; public ACLs and any unreviewed bucket policy are
refused. It creates no bucket/provider/service. No original is written to a public
directory, browser storage or the application filesystem.

Uploads reserve an idempotent PostgreSQL record first, then write a server-keyed
immutable original outside the SQL transaction, then attach the verified storage
version and queue inspection. Failures preserve the reservation/original for
safe retry or operator reconciliation. No automatic deletion occurs on unknown
commit outcomes. Signature checking is not a malware verdict: completed uploads
remain quarantined, cannot be downloaded and are not sent for extraction until
a separately approved trusted scanning worker records a matching clean verdict.
No scanner service is configured or claimed as verified. Downloads require an
authorized clean record, matching inspection/version/digest, bounded object read,
SHA-256 validation and final authorization/safety revalidation.

## Backup, rollback and approval

The preview command `npm run saas:review` opens no database connection and makes
no changes. The guarded initializer requires BOTH an execution flag and the exact
approved SQL checksum. It refuses an occupied port, an existing `.saas-dev`
directory, a stale manifest, a redirected directory, nonempty schemas, unexpected
ownership and existing application roles. Operator DDL creates only the new
cluster/database owner and database before the SQL transaction.

Before applying SQL it creates a custom-format empty-database backup, private
roles backup and SHA-256 inventory under `.saas-dev/backups`, and validates the
archive listing with `pg_restore --list`. That is archive validation, **not a
successful restore drill**. An actual restore drill requires a separately
approved fresh restore target. Backups and database secrets inherit restricted
local ACLs and are excluded from deployment/source inventories.

The migration itself is one transaction; SQL failure rolls back. Initialization
may leave its NEW cluster/database and private recovery material on failure.
There is no automatic DROP, overwrite, deletion or retry. Unknown commit outcomes
require operator inspection. After a committed migration, stop the isolated
service and approve a forward repair or restore into a new target; never restore
over the existing authentication database. No destructive down migration exists.

Approval covers only the exact new target and reviewed SQL. It does not approve
real administrator creation, email delivery, a storage service, production
connections, later business migrations, public financial APIs or deployment.
Published Flutter apps, mobile data, Firebase, production databases, DNS, Vercel
and `D:\vetthevat-backup` remain outside the operation.
